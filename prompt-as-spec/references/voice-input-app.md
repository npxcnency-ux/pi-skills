# 范例：macOS Menubar 语音输入法 Prompt

这是一份**接近"可执行 spec"形态**的 prompt 范例。下方按段拆解每条需求体现的原则。

---

## 原始 Prompt

```bash
claude \
  --dangerously-skip-permissions \
  --output-format=stream-json \
  --verbose \
  -p "请实现一个 macOS menu-bar 语音输入法应用（Swift，macOS 14+），具体要求：

1. 按住 Fn 键录音，松开后将转录文字注入当前聚焦的输入框。优先使用流式转录（Apple Speech Recognition framework）。Fn 键通过 CGEvent tap 全局监听，需抑制 Fn 事件传递以防止触发 emoji 选择器。
2. 默认语言必须为简体中文（zh-CN），确保开箱即用就能识别中文输入。同时在菜单栏提供语言切换选项（英语、简体中文、繁体中文、日语、韩语）。语言选择存储在 UserDefaults 中。
3. 录音时在屏幕底部居中显示一个特别优雅精致的无边框胶囊状悬浮窗，不要有红绿灯和 titlebar。使用 NSPanel（nonactivatingPanel）+ NSVisualEffectView（.hudWindow 材质），高度足够（56px，圆角半径 28px），包含：
   - 左侧 5 根竖条波形动画（44×32px），必须由实时音频 RMS 电平驱动（不要用写死的假动画），说话声音大波形就大、安静时波形就小。各竖条权重为 [0.5, 0.8, 1.0, 0.75, 0.55] 形成自然的中间高两侧低效果，平滑包络（attack 40%、release 15%），每根竖条添加 ±4% 随机抖动增加有机感。波形要足够大，清晰可见。
   - 右侧文字标签（弹性宽度 160-560px）实时显示转录文本，胶囊随文字变多而弹性变宽
   - 入场弹簧动画（0.35s）、文字宽度平滑过渡（0.25s）、退场缩放动画（0.22s）
4. 文字注入使用剪贴板 + 模拟 Cmd+V 粘贴方式，注入前需检测当前输入法：如果是 CJK 输入法，先临时切换到 ASCII 输入源（ABC/US 键盘）再粘贴，粘贴完成后恢复原输入法，防止中文输入法拦截 Cmd+V。注入完成后恢复原剪贴板内容。
5. 接入 LLM 来提升语音识别的准确率，尤其是中英文混杂的情况下。通过 OpenAI 兼容 API（可配置 API Base URL、API Key、Model）对转录文本进行 refine。LLM 的 system prompt 要求非常保守地纠错：只修复明显的语音识别错误（如中文谐音错误、英文技术术语被错误转为中文如「配森」→「Python」、「杰森」→「JSON」），绝对不要改写、润色或删除任何看起来正确的内容，如果输入看起来正确则必须原样返回。
6. 在菜单栏提供 LLM Refinement 子菜单，包含启用/禁用开关和 Settings 入口。Settings 窗口包含 API Base URL、API Key、Model 三个输入框，API Key 输入框要能完全清空，以及 Test 和 Save 按钮。松开 Fn 键后如果 LLM 已启用且已配置，悬浮窗显示 Refining... 状态，等 LLM 返回后再注入最终文本。
7. 应用以 LSUIElement 模式运行（仅菜单栏图标，无 Dock 图标）。使用 Swift Package Manager 构建，提供 Makefile（build/run/install/clean），构建产物为签名的 .app bundle。"
```

## 逐段拆解

### CLI 包装

```bash
--dangerously-skip-permissions   # 不卡权限弹窗
--output-format=stream-json       # 结构化输出
--verbose                          # 留审计痕迹
-p "..."                           # one-shot 模式
```

**体现原则**：把 Claude 当批处理 worker 用，而非聊天。适合长 prompt。

---

### 需求 1：Fn 录音

> 按住 Fn 键录音...通过 **CGEvent tap** 全局监听，需**抑制 Fn 事件传递**以防止**触发 emoji 选择器**。

| 句子 | 体现原则 |
|------|---------|
| "CGEvent tap" | **原则 1（决策前置）**：API 钉死，不让 LLM 在 NSEvent / IOHID / CGEvent 之间犹豫 |
| "抑制 Fn 事件传递" | **原则 4（领域知识注入）**：具体动作 |
| "防止触发 emoji 选择器" | **原则 4 的 why**：解释为什么要抑制，LLM 不知道这个坑 |

---

### 需求 2：默认中文

> 默认语言**必须**为简体中文（zh-CN），确保开箱即用就能识别中文输入。

| 句子 | 体现原则 |
|------|---------|
| "必须" | **类 RFC 2119 措辞**：消除"是否需要默认值"的歧义 |
| "zh-CN" | **原则 1**：locale 代码钉死，不让 LLM 选 zh / zh-Hans |
| "开箱即用就能识别中文" | **原则 4 的 why**：解释为什么不能默认英文 |

---

### 需求 3：悬浮窗（数字密度最高的一段）

> 高度足够（**56px**，圆角半径 **28px**）...波形（**44×32px**）...权重为 **[0.5, 0.8, 1.0, 0.75, 0.55]**...attack **40%**、release **15%**...±**4%** 随机抖动...弹性宽度 **160-560px**...入场 **0.35s**、过渡 **0.25s**、退场 **0.22s**

**体现原则 2（可量化验收点）的极致案例**：一段需求里 10+ 个具体数字，把"优雅精致"全部翻译成了可对比的参数。

**反例约束**：
- "**不要红绿灯和 titlebar**"
- "**不要用写死的假动画**"

**体现原则 3**：精准排除两个 LLM 高概率错误路径。

**决策前置**：
- "NSPanel（nonactivatingPanel）"
- "NSVisualEffectView（.hudWindow 材质）"

**体现原则 1**：连构造函数参数都钉死。

---

### 需求 4：文字注入（典型平台陷阱注入）

> 文字注入使用**剪贴板 + 模拟 Cmd+V**...注入前需检测当前输入法：如果是 CJK 输入法，**先临时切换到 ASCII 输入源**...**防止中文输入法拦截 Cmd+V**。注入完成后**恢复原剪贴板内容**。

| 句子 | 体现原则 |
|------|---------|
| "剪贴板 + Cmd+V" | **原则 1**：明确实现方式，不让 LLM 选 CGEventPost 字符（中文必踩坑） |
| "检测→切换→粘贴→恢复" | **原则 6（时序闭合）**：完整状态机 |
| "防止中文输入法拦截 Cmd+V" | **原则 4 的 why**：领域陷阱解释 |
| "恢复原剪贴板内容" | **原则 5（交付契约）**：副作用必须复原 |

---

### 需求 5：LLM Refine（反例约束的极致）

> system prompt 要求**非常保守地纠错**：只修复明显的语音识别错误（如**「配森」→「Python」、「杰森」→「JSON」**），**绝对不要改写、润色或删除**任何看起来正确的内容，**如果输入看起来正确则必须原样返回**。

| 句子 | 体现原则 |
|------|---------|
| "配森→Python、杰森→JSON" | **原则 4**：用具体例子注入领域知识（中英混杂识别错误的典型模式）|
| "绝对不要改写、润色或删除" | **原则 3（反例约束）**：精准堵 LLM 喜欢"优化"的本能 |
| "如果输入看起来正确则必须原样返回" | **正例兜底**：连"什么都不改"也要显式说，否则 LLM 会觉得"什么都不做不专业" |

这段是 prompt-in-prompt（你给 LLM 的 prompt 里嵌套了 LLM-of-LLM 的 prompt），是写 prompt 中的高级技巧。

---

### 需求 6：UI 流程（时序闭合的典范）

> 松开 Fn → LLM 已启用且已配置 → 悬浮窗显示 **Refining...** 状态 → 等 LLM 返回 → 注入最终文本

**体现原则 6**：一句话把异步流程的状态切换全串了。LLM 不用猜"LLM 调用期间 UI 应该是什么"。

---

### 需求 7：交付契约

> **LSUIElement** 模式...**Swift Package Manager** 构建...提供 **Makefile（build/run/install/clean）**...构建产物为**签名的 .app bundle**。

**体现原则 5**：构建系统、入口点、产物形态、运行模式四件套齐全。

---

## 自检：这份 prompt 还能更好吗？

按 prompt-as-spec 衡量，这份 prompt 已经接近极致，但仍有改进空间：

| 不足 | 建议 |
|------|------|
| 没明确失败路径：LLM 调用失败 / 麦克风权限被拒 / Speech 框架不可用怎么办 | 加一段 "Error handling" |
| 没指定异步并发模型（async-await / Combine / GCD） | 一句话钉死，否则风格会混 |
| 没说 Speech Recognition on-device vs server | 隐私 / 延迟 trade-off 未决，LLM 会猜 |
| 没指定签名方式（ad-hoc / Developer ID） | "签名的 .app" 可能歧义 |
| 单 prompt 7 条需求，颗粒度偏大 | 按 spec-driven-dev 建议拆 3-4 个子任务，每个一个 session |

---

## 最大的启示

**这份 prompt 之所以好，是因为作者已经在脑子里把这个 app 写过一遍了。**

Prompt 是大脑里那份 design doc 的导出，不是问"该怎么做"，而是"我已经想清楚了，你照着做"。

LLM 没有自己思考的空间 → 也就没有跑偏的空间。
